# ADR-002: SQLCipher şifreli SQLite; anahtar SecureStore (THIS_DEVICE_ONLY); Expo Go yerine Development Build
- **Durum:** Kabul edildi
- **Tarih:** 2026-09-03
- **İlgili gereksinimler:** R93.1, R93.2, R93.3, R93.4, R93.5, R93.6, R93.7; dolaylı: R92.5, R92.6 (`.bak` kopyaları şifreli kalır), R95.4 (export ZIP şifresiz), R116.1, R116.3, R117.3 (`DbOpenError`), R118.2. Kabul senaryoları: AT-14, AT-16, AT-18, AT-19 (dolaylı).

## Bağlam

V90 tek kullanıcılı, sunucusuz, offline-first bir uygulamadır; tüm veri cihazdaki SQLite dosyasındadır (02 §1). Bu veri **hassas** sınıfındadır: kan sonuçları (`lab_results`), kilo (`weight_logs`), vücut ölçümleri (`body_measurements`), progress fotoğrafları (`progress_photos` + `documentDirectory/photos/`), sağlık notları (R93.1). Cihazın kaybı, root/jailbreak, yedek dosyalarının üçüncü taraf araçlarla okunması veya başka bir uygulamanın aynı dosya sistemine erişimi durumunda dosyanın düz metin olmaması gerekir.

Kısıtlar:
- R93.2 production native build'lerde **SQLCipher** ister; R93.3 şifreli/şifresiz sağlayıcıların aynı `DatabaseProvider` arayüzünü uygulamasını ister.
- SQLCipher Expo Go içinde çalışmaz (native modül). R93.4, Expo Go uyumluluğu uğruna production güvenliğinden vazgeçmeyi yasaklar.
- R93.5/R93.6: anahtar kaynak kodda veya AsyncStorage'da tutulamaz; iOS Keychain / Android Keystore (`expo-secure-store`) zorunludur.
- R93.7: production'da şifresiz sağlayıcı **build zamanında** engellenir.
- Teknoloji yığını (02 §2): `expo-sqlite` SDK ≥ 52, `useSQLCipher: true` config plugin; testler Node'da `better-sqlite3` / `@journeyapps/sqlcipher` ile aynı SQL üzerinden.

Anahtar yönetimi ayrıca yedekleme (§92, §95) ve cihaz yedeği (iCloud / Google) davranışını belirler: anahtar cihazdan çıkarsa DB dosyasının başka cihazda açılabilmesi kolaylaşır ama anahtar da bulutta dolaşır.

## Karar

### 1. `DatabaseProvider` soyutlaması ve iki sağlayıcı

```
DatabaseProvider { open(): Promise<Db>; close(); path; isEncrypted: boolean }
EncryptedSqliteProvider : expo-sqlite (SQLCipher, useSQLCipher: true) + PRAGMA key
PlainSqliteProvider     : expo-sqlite (düz) — yalnızca __DEV__ && !isProductionBuild
```

- `src/core/db/provider/` altında; repository'ler ve `MigrationRunner` yalnızca `Db` arayüzünü görür (R93.3).
- `open()` sırası (bağlantı başına, migration transaction'larının **dışında**):
  1. `PRAGMA key = "x'<64 hex>'"` — ilk ifade olmak zorundadır. Ham 32 baytlık anahtar `x'…'` blob sözdizimiyle verilir; bare string verilseydi SQLCipher bunu parola sayıp PBKDF2 uygulardı (yavaş ve semantik olarak yanlış).
  2. `PRAGMA journal_mode = WAL; PRAGMA synchronous = FULL; PRAGMA foreign_keys = ON; PRAGMA busy_timeout = 5000`.
  3. `SELECT count(*) FROM sqlite_master` — anahtar yanlışsa burada `SQLITE_NOTADB` → `DbOpenError`.
  4. `MigrationRunner.run()`.

### 2. Anahtar: `DbKeyManager` + `expo-secure-store`, `WHEN_UNLOCKED_THIS_DEVICE_ONLY`

```
DbKeyManager.getOrCreate():
  SecureStore.getItemAsync('v90.dbkey')
  ?? hex(expo-crypto getRandomBytes(32))
     → SecureStore.setItemAsync('v90.dbkey', hex, { keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY })
```

- Anahtar yalnızca bellekte (`open()` süresince) ve SecureStore'da bulunur; log'a yazılmaz, `manifest.json`/`data.json`'a girmez, crash breadcrumb'larına girmez (R93.5, R93.6, R118.2).
- **THIS_DEVICE_ONLY**: iOS'ta anahtar iCloud Keychain'e senkronlanmaz ve cihaz yedeğinden başka cihaza taşınmaz. Android'de SecureStore değeri Keystore'daki dışa aktarılamayan anahtarla şifrelenir; eşdeğer davranış. Sonuç: DB dosyası başka cihaza kopyalansa bile açılamaz. Cihazlar arası taşıma **yalnızca** kullanıcının bilinçli olarak aldığı export ZIP'i ile yapılır (02 §12.3).
- **WHEN_UNLOCKED**: anahtar yalnızca cihaz kilidi açıkken okunur. V90'ın arka planda DB'ye erişen hiçbir yolu yoktur (rest timer bildirimi önceden planlanır — ADR-003), bu nedenle daha kısıtlayıcı seçenek yeterlidir.
- Anahtar rotasyonu (`PRAGMA rekey`) v1 kapsamında değildir; `DbKeyManager.rotate()` arayüzü gelecekte eklenebilir.
- `.bak.v<from>.sqlite` (R92.5) ve `v90.pre-import.sqlite` (02 §12.3) kopyaları aynı anahtarla şifreli dosyalardır; ek işlem gerekmez.

### 3. Build stratejisi: Development Build zorunlu, Expo Go yalnızca UI prototipi

| Profil | Sağlayıcı | Kural |
|--------|-----------|-------|
| `development` (EAS dev client) | `EncryptedSqliteProvider` | Ekip günlük geliştirmeyi gerçek şifreleme ile yapar; SQLCipher'a özgü davranışlar (PRAGMA sırası, `cipher_page_size`, WAL) ilk günden test edilir. |
| `expo-go` | `PlainSqliteProvider` | Yalnızca `__DEV__ && !isProductionBuild`; DB'ye dokunan hiçbir özellik burada "doğrulanmış" sayılmaz. |
| `preview` / `production` | `EncryptedSqliteProvider` | `app.config.ts` → `['expo-sqlite', { useSQLCipher: true }]`. |

R93.7 iki katmanla sağlanır:
1. **Build zamanı:** `babel`/`metro` alias, production bundle'da `PlainSqliteProvider` modülünü boş modüle bağlar; bundle içinde `PlainSqliteProvider` sembolü kalırsa CI testi başarısız olur.
2. **Çalışma zamanı (savunma derinliği):** `assertEncryptedProviderInProduction()` `AppBootstrap` başında `!provider.isEncrypted && !__DEV__` ise `DbOpenError('PLAIN_PROVIDER_IN_PRODUCTION')` fırlatır; uygulama açılmaz.

### 4. Cihaz yedeği ve anahtar kaybı politikası

- Anahtar kaybı (cihaz sıfırlama, Keychain/Keystore silinmesi, uygulama verisinin sistem tarafından temizlenmesi) = **veri kaybı**. Bilinçli tercih: gizlilik > taşınabilirlik. Azaltım: aylık yedek hatırlatması (kapatılabilir) ve `DbOpenError` kurtarma ekranında "Yedekten geri yükle" (02 §15).
- Android'de sistem auto-backup `v90.sqlite*` dosyalarını anahtarsız yeni cihaza taşıyabilir → açılamayan dosya. `android.dataExtractionRules` / `fullBackupContent` ile DB ve `photos/` dizini auto-backup'tan hariç tutulur; böylece yeni cihazda temiz onboarding + import akışı çalışır (02'de tanımlanmamış; bkz. Riskler).
- Export ZIP (R95.4) varsayılan olarak **şifresizdir**; kullanıcı uyarılır, arşivleyici destekliyorsa opsiyonel parola ile ZIP AES sunulur (02 §12.3).

## Değerlendirilen alternatifler

| # | Alternatif | Neden reddedildi |
|---|-----------|------------------|
| A | **Düz SQLite + işletim sistemi dosya şifrelemesi** (iOS Data Protection `NSFileProtectionComplete`, Android FBE). | R93.2 açıkça SQLCipher ister. OS şifrelemesi cihaz kilidi açıkken aynı kullanıcı bağlamındaki her sürece şeffaftır; jailbreak/root ve cihaz yedeği dosyayı düz metin olarak dışarı çıkarır; iki platformda farklı garanti verir. |
| B | **Uygulama düzeyinde alan (kolon) şifrelemesi** — yalnızca hassas kolonlar AES ile şifrelenip `TEXT` olarak saklanır. | `CHECK (final_value_cm > 0)`, indeksler (`ix_meas_site_date`), trend/medyan sorguları, `v_set_effective_load` görünümü şifreli kolonlarda çalışamaz; hangi kolonun hassas olduğu tartışmalıdır (R93.1 listesi geniş); kısmi koruma + yüksek karmaşıklık. |
| C | **Üçüncü taraf SQLite bağlayıcısı** (`@op-engineering/op-sqlite` + SQLCipher, `react-native-quick-sqlite`). | `expo-sqlite`, SDK ≥ 52 ile birinci taraf SQLCipher desteği ve config plugin sunar; EAS/prebuild ile sürtünmesizdir. op-sqlite ek native bağımlılık ve Expo sürüm uyum riski getirir. `DatabaseProvider` soyutlaması sayesinde ileride performans gerekçesiyle geçiş mümkündür; bu ADR'yi değiştirmez. |
| D | **Kullanıcı parolasından türetilen anahtar** (PBKDF2/Argon2), SecureStore yok. | Her açılışta parola istemek hızlı antrenman UX'i (R108) ile çelişir; unutulan parola = kalıcı kayıp; Keychain/Keystore donanım korumasından yararlanılmaz. Opsiyonel ikinci faktör olarak ileride eklenebilir (`PRAGMA rekey`). |
| E | **Anahtar AsyncStorage/MMKV'de veya kaynak kodda.** | R93.5 tarafından yasaktır; MMKV şifrelemesi de kendi anahtarını bir yerde tutmak zorundadır (aynı problem). |
| F | **Expo Go'da geliştirme, yalnızca production'da şifreli sağlayıcı.** | R93.4 ihlali; dev/prod ayrışması: migration, WAL ve `PRAGMA key` sırası gibi SQLCipher'a özgü hatalar ancak release'de görülür; AT-16/AT-14 gerçek sağlayıcıda koşmaz. |
| G | **`AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`** erişilebilirlik sınıfı. | Cihaz kilitliyken de anahtar okunabilir olurdu; şu an arka planda DB erişimi yoktur, dolayısıyla gereksiz gevşetme. Arka plan işi eklenirse bu ADR revize edilir. |
| H | **`WHEN_UNLOCKED`** (iCloud Keychain'e senkronlanabilir). | Anahtar cihazı terk eder (Apple bulutu); Android'de eşdeğeri yoktur → platformlar arası tutarsız garanti; "gizlilik varsayılan" ilkesine (02 §1) aykırı. |

## Sonuçlar

**Olumlu**
- Dosya sistemi, cihaz yedeği ve adli kopyalarda DB düz metin değildir; `progress_photos` metadata'sı ve lab değerleri korunur (R93.1).
- Tek arayüz (`DatabaseProvider`) sayesinde domain/repository kodu şifrelemeden habersizdir; Node testleri aynı SQL'i `@journeyapps/sqlcipher` ile koşar.
- Anahtar hiçbir zaman uygulama sınırlarını aşmaz; import/export akışı anahtardan bağımsızdır.
- Development Build zorunluluğu, SQLCipher/WAL/migration davranışının her gün gerçek koşullarda test edilmesini sağlar.

**Olumsuz**
- Expo Go ile hızlı deneme yalnızca UI katmanı için mümkündür; her geliştiricinin EAS dev client kurması gerekir (ilk kurulum maliyeti, native değişikliklerde yeniden build).
- SQLCipher yazma/okuma maliyeti (~%5–15) + `synchronous = FULL` fsync maliyeti; set başına tek küçük transaction olduğu için pratikte < 10 ms (02 §7.1).
- Anahtar kaybı geri döndürülemez; kullanıcı yedek almadıysa veri gider.
- Cihaz değişiminde otomatik devam yoktur; kullanıcı export/import yapmak zorundadır.

**Riskler ve azaltımlar**
- *iOS soğuk açılışta "protected data unavailable" (ilk kilit açılmadan önce) Keychain `nil` döner.* → `DbKeyManager` bu durumu `KeyUnavailableError` olarak ayırır; `AppBootstrap` kısa bekleme/yeniden deneme yapar ve **yeni anahtar üretmez** (aksi halde mevcut DB kalıcı olarak açılamaz hale gelir).
- *Yanlış anahtar / bozuk dosya ayrımı.* → `SQLITE_NOTADB` → `DbOpenError` (02 §15): "Veritabanı açılamadı." + Yeniden dene · Yedekten geri yükle; anahtar asla otomatik sıfırlanmaz.
- *Android auto-backup şifreli dosyayı anahtarsız taşır.* → DB ve `photos/` backup kurallarından hariç tutulur (Karar 4).
- *SQLCipher sürüm farkı (expo-sqlite ↔ Node test bağlayıcısı).* → `PRAGMA cipher_version` çıktısı CI'da loglanır; sürümler `package.json`'da sabitlenir; `cipher_page_size`/KDF varsayılanları ham anahtar kullanıldığı için etkisizdir.
- *Migration öncesi `.bak` kopyası WAL dosyasını dışarıda bırakır.* → Kopyadan önce `PRAGMA wal_checkpoint(TRUNCATE)` (03 §2).
- *Production bundle'a `PlainSqliteProvider` sızar.* → CI: production bundle string taraması + `assertEncryptedProviderInProduction()` unit testi.
- *Bellekte anahtar sızıntısı (crash dump).* → Anahtar `open()` sonrası referanssız bırakılır; crash reporter yok (v1, R118); eklenirse `beforeSend` temizliği.
