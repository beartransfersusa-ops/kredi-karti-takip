# ADR-004: Veritabanı tek doğruluk kaynağıdır: komut modeli, anında transaction, bellekte tamponlama yok
- **Durum:** Kabul edildi
- **Tarih:** 2026-09-03
- **İlgili gereksinimler:** R90.1, R90.2, R90.3, R90.4, R90.5, R90.6, R90.7, R117.1, R117.2, R117.3, R117.4, R117.5; dolaylı: R88.6 (`advanceSequence` aynı tx), R91.8, R92.3, R107.1 (PR tespiti aynı tx), R112.3, R113.2. Kabul senaryoları: AT-01, AT-02, AT-15 (hata sınıflandırma), AT-18.

## Bağlam

Bir hipertrofi uygulamasında en kötü kullanıcı deneyimi, salonda girilen setin kaybolmasıdır. React Native uygulamaları arka planda sık sık öldürülür; telefon yeniden başlatılabilir; JS istisnası uygulamayı çökertebilir; kullanıcı yanlışlıkla geri tuşuna basabilir. Yaygın ama yanlış desen, aktif antrenmanı bir in-memory store'da (Zustand/Redux) tutup "Antrenmanı Bitir" anında toplu kaydetmektir; R90.6 bunu açıkça yasaklar ve R90.1 her işlemin **anında** yerel DB'ye yazılmasını ister. R90.7, UI state'i DB'nin türevi olarak tanımlar: tek doğruluk kaynağı DB'dir.

Buna bağlı ikincil gereksinimler:
- Uygulama yeniden açıldığında aktif oturum **yalnızca DB'den** geri yüklenir; "Devam eden antrenmanın var." kartı üç seçenek sunar (R90.3–R90.5).
- Her DB hatası sınıflandırılır, Türkçe mesaj ve güvenli retry sunulur; beyaz ekran yasaktır (R117.1–R117.5). Retry'ın aynı seti iki kez yazmaması gerekir.
- Sıra ilerletme (R88.6), PR tespiti (R107), rest timer başlatma (R91) gibi yan etkiler set kaydıyla tutarlı olmalıdır.

02 §3 transaction kuralını ("kullanıcıya görünen her eylem tek `db.withTransaction`"), §7.1 komut tablosunu ve dayanıklılık ayarlarını (`WAL` + `synchronous = FULL`), §15 hata taksonomisini ve `commandId` idempotency'sini tanımlar. 03 §0/§1.1 `BEGIN IMMEDIATE … COMMIT` kuralını, `command_log` tablosunu ve `set_logs.command_id UNIQUE` kısıtını verir.

## Karar

### 1. Her kullanıcı eylemi bir **komut**tur

```ts
interface Command<T extends CommandType> {
  commandId: string;        // uuid v4, UI'da butona basıldığı anda üretilir
  type: T;                  // 'completeSet' | 'editSet' | 'substituteExercise' | 'skipExercise' | 'reorderExercises'
                            // | 'startRest' | 'skipRest' | 'setNote' | 'draftInput'
                            // | 'reschedule' | 'skipWorkout' | 'finishSession' | 'cancelSession' | 'pause' | 'resume' | …
  payload: CommandPayload[T];
  occurredAtUtc: string; localDateKey: string; timeZone: string;   // Timestamped (02 §5.1)
}
```

- Komutlar `domain/workout/ActiveSessionService`, `SetLogService`, `RestTimerService`, `domain/program/*` servislerinde yürütülür. `features/` katmanı yalnızca servis çağırır; repository'lere doğrudan erişemez (lint kuralı).
- Komut yürütmesi = **tam olarak bir** `db.withTransaction(async tx => …)` → `BEGIN IMMEDIATE … COMMIT`. Transaction sınırını servis belirler; repository metotları `tx` alır (02 §3). Birlikte anlamlı olan tüm yan etkiler aynı tx içindedir:

| Komut | Aynı transaction içinde yazılanlar |
|-------|-----------------------------------|
| `completeSet` | `command_log` INSERT → `set_logs` INSERT → `PrDetector` (`personal_records`) → önceki `rest_timers` kapat + yeni `running` INSERT → `session_exercises.status/draft_*` temizle |
| `editSet` | `command_log` → `set_logs` UPDATE → `set_log_revisions` INSERT |
| `substituteExercise` | `command_log` → `session_exercises.exercise_id` UPDATE, `original_exercise_id` korunur |
| `finishSession (completed)` | `command_log` → `workout_sessions` UPDATE → `scheduled_workouts.status` → `advanceSequence()` + `sequence_events` |
| `reschedule` | `command_log` → eski satır `rescheduled` → yeni `planned` (sıra önemli, 03 §1.5) |

### 2. İdempotency: `command_log` + `set_logs.command_id`

- Transaction'ın ilk ifadesi `INSERT INTO command_log(command_id, command_type, executed_at_utc)`; çakışma (`SQLITE_CONSTRAINT`) → komut daha önce uygulanmıştır → transaction geri alınır ve önceki sonuç döndürülür (no-op).
- En kritik komut için ikinci koruma: `set_logs.command_id UNIQUE` (03 §1.6). `UNIQUE (session_exercise_id, set_index, side)` ayrıca çift dokunma ile aynı setin iki kez yazılmasını engeller.
- `DbWriteError` sonrası "Yeniden dene" **aynı** `commandId` ile gönderir; UI yeni kimlik üretmez (R117.4; 02 §15).
- `command_log` yedeğe dahil değildir (`TableRegistry` dışı, 03 §4) ve 30 günden eski satırlar açılışta budanır.

### 3. Bellekte tamponlama yok; store DB'nin projeksiyonudur

- `useActiveWorkoutStore` yalnızca `hydrate()` ile dolar: komut commit edildikten **sonra** ilgili satırlar yeniden okunur ve store güncellenir. Optimistic update yoktur; write-behind kuyruğu yoktur; "kaydedilecekler" listesi yoktur (R90.7). SQLite yerel olduğu için gecikme < 10 ms'dir (02 §7.1).
- Transaction başarısız olursa store **değişmez** — store her zaman son commit edilmiş durumu yansıtır; UI hata bandı gösterir.
- `AppState → background/inactive` geçişinde kaydedilecek bir şey yoktur; yalnızca `flushDraftInputs()` çağrılır (R90.2).
- **Tek istisna — taslak girdiler:** `NumericStepper`'da yazılmakta olan ama henüz "Seti Tamamla" ile commit edilmemiş değer (`draftInput` komutu) ≤ 300 ms debounce ile `session_exercises.draft_load_json / draft_reps / draft_rir` alanlarına yazılır. Debounce penceresi bellekte tutulan **tek** durumdur; şu noktalarda zorunlu flush edilir: `AppState` değişimi, ekran blur, başka herhangi bir komuttan hemen önce. Taslak bir kayıt değil, kolaylıktır; kaybı en fazla 300 ms'lik tuş girişidir (R90.1 "anında" bu sınır içinde sağlanır).

### 4. Dayanıklılık ayarları bağlantı düzeyinde

- `EncryptedSqliteProvider.open()` her bağlantıda `PRAGMA journal_mode = WAL; PRAGMA synchronous = FULL; PRAGMA foreign_keys = ON; PRAGMA busy_timeout = 5000` çalıştırır — migration transaction'larının **dışında** (bu PRAGMA'lar transaction içinde etkisizdir; bkz. ADR-002).
- Süreç ölümü (crash) → WAL sayesinde son `COMMIT` korunur; ani güç kaybı / telefon restart → `synchronous = FULL` fsync sayesinde korunur (R90.2). Yarım kalan transaction (örn. `set_logs` yazıldı, `personal_records` yazılmadan crash) atomik olarak geri alınır: set ya tamamen vardır ya hiç yoktur; `commandId` ile güvenle tekrarlanır.
- Tek yazma bağlantısı; komutlar servis katmanında **seri** yürütülür (aynı anda iki `withTransaction` başlatılmaz), böylece `SQLITE_BUSY` pratikte oluşmaz.

### 5. Aktif oturum yaşam döngüsü DB'den yönetilir

- `ux_sessions_single_active` (03 §1.6): en fazla bir `workout_sessions.status = 'active'`.
- `AppBootstrap` → `ActiveSessionService.findActive()` → varsa **"Devam eden antrenmanın var."** kartı: **Devam Et** (ekrana git, `hydrate()`), **Antrenmanı Bitir** (özet → `completed`/`partial`, `ended_reason = 'resumeCardFinish'`), **Antrenmanı İptal Et** (onay → `status = 'cancelled'`, `ended_reason = 'resumeCardCancel'`; setler silinmez, `set_logs.discarded = 1`; plan `planned`'a döner) (R90.3–R90.5).
- `startedAtUtc`, `completedAtUtc`, `calendarDateKey`, `timeZone`, `utcOffsetMinutes` oturum satırında ayrı alanlardır (R112.3, R113.2).

### 6. Hata sınıflandırma ve beyaz ekran yasağı

| Hata | Yakalama | Kullanıcı mesajı | Aksiyon |
|------|----------|------------------|---------|
| `DbWriteError` (`SQLITE_FULL`, `SQLITE_BUSY`, `SQLITE_IOERR`) | Repository → servis | "Kaydedilemedi. Boş alanı kontrol et." | Yeniden dene (aynı `commandId`) |
| `DbConstraintError` (unique/CHECK) | Servis | "Bu set zaten kayıtlı." / alan mesajı | Ekranı DB'den yenile (`hydrate()`) |
| `DbOpenError`, `MigrationFailedError` | `AppBootstrap` / `MigrationRunner` | 02 §15 | Kurtarma ekranı |
| Beklenmeyen render hatası | Kök `ErrorBoundary` (DB bağımsız) | "Bir şeyler ters gitti." | Yeniden yükle · Ana ekrana dön |

Kök `ErrorBoundary` DB'ye, ağa ve store'a bağımlı değildir; bu nedenle beyaz ekran imkânsızdır (R117.1, R117.2). Mesajlar Türkçe; teknik ayrıntı "Ayrıntılar" altında (R117.5).

## Değerlendirilen alternatifler

| # | Alternatif | Neden reddedildi |
|---|-----------|------------------|
| A | **Bellek-öncelikli store + periyodik autosave** (her N saniye / arka plana geçişte / oturum sonunda toplu yazma). | Her aralık bir kayıp penceresidir; crash iki kayıt arasında olursa setler gider (R90.2); toplu yazma R90.6'yı ihlal eder; `AppState` olayları crash'te tetiklenmez; kısmi kaydedilmiş toplu yazmada çoğaltma/tutarsızlık. |
| B | **Optimistic UI + write-behind kuyruğu** (store hemen güncellenir, DB yazımı arkada). | Kuyruk bellektedir ve crash'te kaybolur; başarısızlıkta store'u geri alma (reconcile) karmaşıklığı; SQLite yerel ve < 10 ms olduğundan optimistic güncellemenin kullanıcıya hissedilir kazancı yoktur; DB ile store ayrışabilir (R90.7 ihlali). |
| C | **Tam event sourcing** (yalnızca `events` append-only tablosu, durum bellekte projeksiyon, snapshot'lar). | Her açılışta projeksiyon; motorlar (`ProgressionEngine`, `v_set_effective_load`, `v_weekly_direct_sets`) ilişkisel şekle ihtiyaç duyar; event şeması migration'ı (§92) zorlaşır; yedek/format (§95) `TableRegistry` ile tablo bazlıdır. Bunun yerine **seçici denetim tabloları** benimsenir: `command_log`, `sequence_events`, `set_log_revisions`, `settings_history` — izlenebilirlik projeksiyon maliyeti olmadan sağlanır. |
| D | **Zustand `persist` (AsyncStorage/MMKV)** ile oturum state'i, DB'ye antrenman sonunda yazma. | Şifresiz depolama (R93); ikinci doğruluk kaynağı (R90.7); transaction ve kısıt (`ux_sessions_single_active`, `UNIQUE set_index`) yok; sonda toplu yazma R90.6 ihlali; `persist` yazımı da asenkron ve debounce'ludur (kayıp penceresi). |
| E | **Change-tracking ORM / reaktif DB** (WatermelonDB, TypeORM unit-of-work). | Yazmaları kendi batch/lazy mekanizmasında toplar ve transaction sınırını gizler; SQLCipher + `expo-sqlite` uyumu belirsiz; migration modeli §92 ile örtüşmez. Sorgu oluşturucu olarak Drizzle ileride kabul edilebilir, ancak `withTransaction` sınırı açık ve servis tarafından belirlenmiş kalmak şartıyla; change-tracking yok. |

## Sonuçlar

**Olumlu**
- AT-01/AT-02 tasarım gereği sağlanır: her set kendi transaction'ında diskte; geri yükleme tek bir `SELECT`.
- İdempotent komutlar sayesinde retry güvenlidir; "acaba iki kez mi kaydedildi?" belirsizliği yoktur.
- Domain servisleri React'ten bağımsızdır; Node'da in-memory repo ile hızlı, deterministik test (02 §3, §16).
- Set + PR + rest timer + sıra ilerletme atomik olduğundan tutarsız ara durumlar (set var, timer yok; sıra ilerledi, plan açık) oluşamaz.
- Denetim tabloları (`set_log_revisions`, `sequence_events`) açıklanabilirlik (R122) ve destek/hata ayıklama için hazır veri sağlar.

**Olumsuz**
- Daha fazla küçük yazma: her set commit'i bir fsync (`synchronous = FULL`); ölçülen maliyet birkaç ms, R108.4 (3–5 s/set) hedefine göre ihmal edilebilir.
- Her komuttan sonra `hydrate()` — küçük ama sürekli okuma yükü; yalnızca etkilenen satırlar okunur.
- Kod hacmi: her eylem için komut tipi, payload şeması (Zod) ve servis metodu; "sadece store'u güncelle" kısayolu yoktur.
- Taslak debounce (Karar 3) ilkeye açık bir istisna oluşturur ve belgelenmek zorundadır.

**Riskler ve azaltımlar**
- *Geliştirici transaction'ı atlayıp repository'ye doğrudan yazar.* → Lint: `features/**` `core/db/repositories/**` import edemez; repository metotları `tx` parametresini zorunlu kılar (tip düzeyinde `Db` değil `Tx` alır).
- *İç içe `withTransaction`.* → İç çağrı `SAVEPOINT` kullanır veya geliştirme ortamında fırlatır; test ile korunur.
- *Uzun transaction UI'ı bloklar.* → Komut tx'leri yalnızca yazma + küçük okuma içerir; `PrDetector` sorguları `ix_setlogs_exercise_time` ile indekslidir; analitik hesaplar (adherence, trend) tx dışında ve ayrı okuma ile yapılır.
- *Çift dokunma "Seti Tamamla" → iki farklı `commandId`.* → Buton commit tamamlanana kadar devre dışı; `UNIQUE (session_exercise_id, set_index, side)` ikinci koruma.
- *Disk dolu (`SQLITE_FULL`).* → `DbWriteError` + Türkçe mesaj + retry; taslak alanlar kaybolabilir ama commit edilmiş setler güvendedir; ayrıca fotoğraf kaydı öncesi boş alan kontrolü.
- *Store ile DB ayrışır (bug).* → Property test: rastgele komut dizisi sonrası `hydrate()` çıktısı == store; geliştirme modunda her komut sonrası derin eşitlik assert'i.
- *`command_log` sınırsız büyür.* → 30 günlük budama (Karar 2); tablo yedeğe dahil değildir.
