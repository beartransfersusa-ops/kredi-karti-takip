# ADR-006: İleri-yalnız, idempotent, checksum'lu migration'lar ve migration öncesi dosya yedeği
- **Durum:** Kabul edildi
- **Tarih:** 2026-09-03
- **İlgili gereksinimler:** R92.1, R92.2, R92.3, R92.4, R92.5, R92.6, R92.7 (birincil); R90.2, R93.2, R93.6, R95.8, R111.3, R117.1, R117.3, R117.5, R124.1 (ilişkili); kabul senaryosu AT-16

## Bağlam

- Şema ilk sürümde dondurulup bırakılamaz (R92.1); `01-specification.md` örnek migration adları verir: `001_initial`, `002_add_workout_state`, `003_add_lab_results`. `03-data-model.md §1` şema sürümü 1'in (`001_initial`) tam DDL'ini, §2 ise migration kurallarını ve runner sözleşmesini tanımlar; `02-architecture.md §12.1` `MigrationRunner.run()` akışını verir.
- Kullanıcılar offline'dır ve uygulama sürümlerini atlayabilir (ör. şema 1'den doğrudan 4'e). Runner, bekleyen tüm migration'ları sırayla ve güvenle çalıştırmak zorundadır.
- Veri hassastır (R93.1) ve tek kopyadır (sunucu yok). R92.4: yeni sürüm eski veriyi silemez; R92.6: migration başarısız olursa veri bozulmaz, transaction geri alınır ve/veya yedekten dönülür, Türkçe kurtarma ekranı gösterilir.
- SQLite'ın özellikleri kararı şekillendirir: DDL transaction içinde çalışır (`ROLLBACK` DDL'i de geri alır); `ALTER TABLE` sınırlıdır (kolon tipi/CHECK değişikliği, eski sürümlerde `DROP COLUMN` yok → tablo yeniden kurma deseni gerekir); `PRAGMA journal_mode`, `PRAGMA foreign_keys` gibi bağlantı düzeyi PRAGMA'lar transaction içinde değiştirilemez; WAL modunda dosya kopyası öncesi checkpoint gerekir.
- DB SQLCipher ile şifrelidir (R93.2); dosya kopyası da şifrelidir ve aynı anahtarla açılır (02 §12.2).
- DB testleri Node'da aynı SQL dosyalarıyla çalışır (02 §2, §16); migration'lar React Native'e bağımlı olmamalıdır.
- Yedek formatı (`data.json`) da şema sürümü taşır; R95.8 eski yedeklerin aynı migration zinciriyle yükseltilmesini ister. 03 §2 bunun için `core/backup/migrators/00k.ts` (`BACKUP_MIGRATORS[k]`) tanımlar (bkz. ADR-005).

## Karar

### K1. Migration sözleşmesi: ileri-yalnız, sıralı, değişmez

```ts
interface Migration {
  version: number;                 // 1, 2, 3 … boşluksuz artan
  name: string;                    // '001_initial', '002_add_workout_state', …
  up: (tx: Tx) => Promise<void>;   // idempotent; DOWN yok
  checksum: string;                // dosya içeriğinin SHA-256'sı, build zamanında üretilip gömülür
}
export const MIGRATIONS: readonly Migration[] = [m001Initial /* , m002… */];
```

- **`down` yoktur.** Geri dönüş yolu, migration öncesi dosya yedeğidir (K3). Uygulama, DB'nin beklediğinden eski bir şemayla **çalışmaz** (03 §2).
- `MIGRATIONS` dizisi değişmez geçmiştir: yayınlanmış bir migration dosyası bir daha düzenlenmez; düzeltme yeni bir migration'dır.
- Migration dosyaları yalnızca SQL ve `Tx` üzerinden çalışan yardımcılar (`hasColumn(tx, table, col)`, `hasTable`, `hasIndex`) kullanır; React/Expo import'u yasaktır (Node testleri, 02 §16).
- Seed kataloğu güncellemeleri (`exercises.seed_version`, `food_items.seed_version`) migration **değildir**; şemadan bağımsız, `custom_edited = 1` / `is_custom = 1` satırlarını atlayan ayrı bir seed senkronu olarak çalışır (R111.3). Migration'lar yalnızca şema ve şemaya bağlı zorunlu veri dönüşümlerini içerir.

### K2. İdempotency kuralları (R92.3)

- Yalnızca `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `CREATE VIEW IF NOT EXISTS`; kolon eklerken `hasColumn` kontrolü; veri dönüşümlerinde `WHERE` ile zaten dönüşmüş satırları atlama (03 §2).
- SQLite'ın desteklemediği `ALTER` işlemleri için **tablo yeniden kurma deseni**: `CREATE TABLE IF NOT EXISTS <t>_new …` → `INSERT OR IGNORE INTO <t>_new SELECT … FROM <t>` → `DROP TABLE <t>` → `ALTER TABLE <t>_new RENAME TO <t>` → index/view'lar yeniden oluşturulur; her adım `hasTable` ile korunur, böylece yarım kalan bir denemenin tekrarı güvenlidir. Bu deseni kullanan migration `rebuildsTables: true` bayrağı taşır; runner o migration için transaction dışında `PRAGMA foreign_keys = OFF` yapar, `COMMIT` öncesi `PRAGMA foreign_key_check` çalıştırır (boş olmalı) ve sonrasında `ON`'a döner.
- Bağlantı düzeyi PRAGMA'lar (`journal_mode = WAL`, `synchronous = FULL`, `foreign_keys = ON`) migration içinde değil, `EncryptedSqliteProvider.open()` içinde ayarlanır; migration dosyaları yalnızca DDL/DML içerir.

### K3. Runner akışı (`MigrationRunner.run()`), her açılışta

1. **Bütünlük:** `PRAGMA user_version` ve `schema_migrations(version, name, checksum, applied_at_utc)` okunur. Uygulanmış her sürüm için `schema_migrations.checksum` ile `MIGRATIONS[k].checksum` karşılaştırılır; uyuşmazlık → `DbIntegrityError`. `user_version != MAX(schema_migrations.version)` → `DbIntegrityError` (bu iki değer her zaman aynı transaction'da yazıldığından uyuşmazlık yalnızca dış müdahale/bozulma anlamına gelir; runner tahmin yürütmez). `schema_migrations`'ta bilinmeyen (kodda olmayan) bir sürüm varsa DB daha yeni bir uygulama tarafından yazılmıştır → `DbIntegrityError` ("Uygulamayı güncelle").
2. **Bekleyen migration yoksa** çıkılır (no-op; `latest → latest` testinin garantisi).
3. **Dosya yedeği (R92.5):** `PRAGMA wal_checkpoint(TRUNCATE)` → DB kapatılır → `expo-file-system copyAsync(v90.sqlite → v90.bak.v<from>.sqlite)` → kopya boyutu doğrulanır → DB yeniden açılır. Kopya için boş alan `2 × DB boyutu`'nun altındaysa veya kopya başarısızsa migration **başlamaz**; `MigrationFailedScreen` "Alan yetersiz" varyantı gösterilir ("Alan aç ve tekrar dene" · "Yedeği dışa aktar"). Yedeksiz migration yoktur. En fazla bir `.bak` tutulur (yenisi eskisinin yerine geçer).
4. **Her migration ayrı transaction:** `BEGIN IMMEDIATE` → `up(tx)` → `INSERT INTO schema_migrations` → `PRAGMA user_version = v` → `COMMIT`. `user_version` ve `schema_migrations` **aynı** transaction'dadır.
5. **Hata:** `ROLLBACK` → DB kapatılır → `v90.bak.v<from>.sqlite` geri kopyalanır (`-wal`/`-shm` artıkları silinir) → `MigrationFailedError` → `MigrationFailedScreen`: *"Veritabanı güncellenemedi. Verilerin güvende; uygulamayı güncelleyip tekrar dene."* + **"Yedeği dışa aktar"** + **"Tekrar dene"** (02 §12.1, §15). Uygulama eski şemayla çalışmaz; ana akışa geçilmez.
6. **Başarı:** `.bak` 7 gün sonra silinir (bir sonraki açılışta zaman kontrolü ile).

### K4. `MigrationFailedScreen` → "Yedeği dışa aktar"

Bu ekran yeni uygulama kodunun eski şemaya karşı çalıştığı tek yerdir. Export burada `TableRegistry`'nin güncel Zod satır şemalarını **zorlamaz**: tablolar `sqlite_master`'dan okunur, satırlar ham `SELECT *` ile alınır, manifest'e DB'nin gerçek `PRAGMA user_version`'ı yazılır. Üretilen ZIP, uygulama güncellendikten sonra `BACKUP_MIGRATORS` zinciriyle normal yoldan içe aktarılır (ADR-005 K4).

### K5. Backup migrator paritesi (R95.8)

Her `MIGRATIONS[k]` için `core/backup/migrators/00k.ts` içinde `BACKUP_MIGRATORS[k]` bulunmak zorundadır (lint). İki dönüşüm eş sürümlüdür; ADR-005'teki parite testi bunları birbirine bağlar.

### K6. Test fixture'ları (R92.7)

Her yeni migration eklendiğinde bir önceki sürüm için `test/fixtures/db/v00k.sql` (şema + temsili veri) dondurulur. Test seti: `fresh → latest`, `v(k) → latest ∀k`, `latest → latest` (no-op), `fail-injection@k` (veri değişmedi), `checksum-tamper` (`DbIntegrityError`), `double-run` (aynı `up` iki kez → aynı şema, aynı satırlar).

## Değerlendirilen alternatifler (en az 2; her biri için neden reddedildi)

**A. Çift yönlü (up/down) migration'lar**
Reddedildi: SQLite'ta `down` çoğu zaman kayıplıdır (eklenen kolonu düşürmek veriyi siler → R92.4 ile çelişir); `down`'lar nadiren gerçek veriyle test edilir ve ikinci bir hata yüzeyi açar. Dosya yedeği (`.bak`) daha güçlü ve daha basit bir geri dönüş yoludur: tam byte-düzeyi geri alma, şema bilgisi gerektirmez. Uygulama zaten eski şemayla çalışmayacağı için "geri alıp eski sürümle devam" senaryosu yoktur.

**B. ORM tabanlı otomatik şema senkronu (schema diff / `synchronize`)**
Reddedildi: fark üreticileri kolon tipi değişikliği için tabloyu düşürüp yeniden yaratabilir (sessiz veri kaybı, R92.4 ihlali); üretilen SQL deterministik ve gözden geçirilebilir değildir; idempotency ve `fail-injection` testleri yazılamaz; React Native + SQLCipher ortamında ORM katmanı bağımlılık riski ekler. Elle yazılmış, checksum'lu SQL migration'lar (R92.3 "test edilmiş") gözden geçirme ve test için tek yoldur.

**C. Yalnızca `PRAGMA user_version` (tablo ve checksum yok)**
Reddedildi: R92.2 açıkça `schema_migrations` tablosu + `user_version` ister. Tek sayı, hangi migration'ın ne zaman uygulandığını ve uygulanan dosyanın kodla aynı olup olmadığını söyleyemez; yerinde düzenlenmiş bir migration farklı cihazlarda farklı şemalar üretir ve bunu kimse fark etmez. Checksum bu sessiz sürüklenmeyi `DbIntegrityError` ile görünür kılar.

**D. Dosya yedeği olmadan yalnızca transaction'a güvenmek**
Reddedildi: transaction yalnızca tek migration'ın atomikliğini korur; zincirin ortasında crash, bozuk sayfa, disk dolu (`SQLITE_FULL`) veya tablo yeniden kurma sırasında `foreign_keys = OFF` iken oluşan mantıksal hatalar transaction'la geri alınamaz. R92.5 "mümkünse dosya kopyası" ister; kararımız "yedeksiz başlama"dır, çünkü veri tek kopyadır.

**E. Tüm bekleyen migration'ları tek büyük transaction'da çalıştırmak**
Reddedildi: birden çok tablo yeniden kurma içeren zincirde WAL dosyası ve kilit süresi büyür; hata anında hangi sürümde kalındığı bilgisi kaybolur; kısmi ilerleme (`.bak` + `schema_migrations`) ile "Tekrar dene" kaldığı yerden devam edemez. Migration başına transaction + tek dosya yedeği hem atomiklik hem tanılanabilirlik sağlar.

**F. Migration'ı açılışta değil, arka planda/tembel çalıştırmak**
Reddedildi: kod yeni şemayı bekler; eski şemada bir sorgu `SQLITE_ERROR` üretir ve R117.1 (beyaz ekran yok) riskini büyütür. Açılışta, `AppBootstrap` içinde ve ilerleme göstergesiyle çalıştırmak tek güvenli yoldur.

## Sonuçlar (olumlu / olumsuz / riskler ve azaltımlar)

**Olumlu**
- Eski veri hiçbir yolda silinmez: transaction rollback + dosya geri yükleme (R92.4, R92.6, AT-16).
- Sürüm atlayan kullanıcılar için zincir deterministiktir; `v(k) → latest` testleri her sürüm için otomatik çalışır (R92.7).
- Checksum, yerinde düzenlenmiş migration'ları ve dış müdahaleyi görünür kılar; `schema_migrations` denetim izi sağlar (R92.2).
- Migration'lar Node'da aynı SQL ile test edilir; React Native cihaz döngüsü gerekmez.
- Backup migrator paritesi sayesinde yedekler de zincirle yükselir (R95.8).

**Olumsuz**
- Her migration için yedek kopya (WAL checkpoint + kopya) açılışı DB boyutuyla orantılı geciktirir (tipik <100 MB için saniyeler); ilerleme ekranı gerekir.
- Geçici olarak 2× DB disk alanı gerekir; yetersiz alanda migration başlamaz.
- Her migration için üç ek yapıt (fixture, backup migrator, test) bakım yükü getirir; lint bunu zorunlu kılar.
- `down` olmadığı için geliştirme sırasında "geri al" yerine DB'yi silip yeniden kurmak gerekir (yalnızca geliştirici deneyimi).

**Riskler ve azaltımlar**

| Risk | Azaltım |
|------|---------|
| `.bak` geri kopyalanırken crash → hem DB hem `.bak` şüpheli | Geri yükleme "kopyala → doğrula (`PRAGMA quick_check`) → yeniden adlandır" sırasıyla yapılır; `.bak` geri yükleme başarılı doğrulanana kadar silinmez. |
| WAL checkpoint yapılmadan kopya alınır → `.bak` eksik commit içerir | K3-3 `wal_checkpoint(TRUNCATE)` + DB kapatma zorunlu; test kopya sonrası `-wal` dosyasının boş olduğunu doğrular. |
| Tablo yeniden kurma sırasında FK ihlali `foreign_keys = OFF` nedeniyle görünmez | `rebuildsTables` bayrağı; `COMMIT` öncesi `PRAGMA foreign_key_check` zorunlu, boş değilse `ROLLBACK`. |
| Geliştirici yayınlanmış migration'ı düzenler | Checksum uyuşmazlığı `DbIntegrityError`; CI'da `MIGRATIONS` checksum'ları git geçmişiyle karşılaştıran test ("published migration changed"). |
| `MigrationFailedScreen` export'u yeni Zod şemalarıyla eski satırları reddeder | K4: ham export, gevşek doğrulama, gerçek `user_version` manifest'e yazılır. |
| Seed güncellemesi migration'a karışır ve kullanıcı override'larını ezer | K1: seed senkronu ayrı; `custom_edited`/`is_custom` satırları atlanır (R111.3); test seed senkronunun bu satırları değiştirmediğini doğrular. |
| SQLCipher sürüm değişimi DB dosya formatını değiştirir | `EncryptedSqliteProvider.open()` başarısızsa `DbOpenError` (02 §15); SQLCipher yükseltmeleri ayrı ADR ve `PRAGMA cipher_migrate` planı ister. |

## Doğrulama (hangi test/kabul senaryosu bu kararı doğrular)

- **AT-16** (integration + manuel): eski sürüm fixture DB'si ile uygulama güncellenir → tüm satırlar korunur, `schema_migrations` ve `user_version` en son sürümü gösterir; set/oturum/ölçüm ekranları eski veriyi gösterir.
- **R92.7(a)** `fresh → latest`: boş DB'den en son sürüme; `sqlite_master` beklenen tablo/index/view listesiyle eşit; `TableRegistry` anahtarları ile birebir (03 §4).
- **R92.7(b)** `v(k) → latest ∀k`: her `test/fixtures/db/v00k.sql` için `assertRowsPreserved()` (satır sayıları ve içerik).
- **R92.7(c)** idempotency: her migration'ın `up()`'ı iki kez çalıştırılır → hata yok, şema ve veri aynı; `latest → latest` no-op.
- **fail-injection@k:** `MIGRATIONS[k].up` içine hata enjekte edilir → `ROLLBACK`, `.bak` geri yüklenir, DB byte-hash'i migration öncesiyle aynı, `MigrationFailedError` fırlatılır ve `MigrationFailedScreen` render edilir (RNTL).
- **checksum-tamper:** `schema_migrations.checksum` değiştirilir → açılışta `DbIntegrityError`; `user_version` ile `MAX(version)` uyuşmazlığı → `DbIntegrityError`.
- **backup-before-migrate:** bekleyen migration varken `v90.bak.v<from>.sqlite` oluşur, `-wal` boştur, `.bak` aynı anahtarla açılır ve `PRAGMA quick_check = ok`; kopya başarısızlığı simüle edildiğinde migration başlamaz ve "Alan yetersiz" ekranı gösterilir.
- **rebuild-fk:** tablo yeniden kurma deseni içeren örnek migration için `foreign_key_check` boş; kasıtlı FK ihlali enjekte edildiğinde `ROLLBACK`.
- **Lint:** her `MIGRATIONS[k]` için `BACKUP_MIGRATORS[k]` mevcut; migration dosyalarında React/Expo import'u yok.
- **Manuel (05-acceptance-tests.md):** gerçek cihazda düşük disk alanı ile güncelleme; "Yedeği dışa aktar" ile üretilen ZIP'in güncel sürümde içe aktarılabilmesi.
