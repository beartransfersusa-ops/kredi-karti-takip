# ADR-005: Yedek formatı ZIP (manifest.json + data.json + photos/) ve staging DB ile atomik değişim
- **Durum:** Kabul edildi
- **Tarih:** 2026-09-03
- **İlgili gereksinimler:** R95.1, R95.2, R95.3, R95.4, R95.5, R95.6, R95.7, R95.8 (birincil); R92.4, R92.6, R93.5, R93.6, R112.2, R116.1, R116.3, R116.4, R117.3, R117.4, R117.5, R119.4, R124.1 (ilişkili); kabul senaryoları AT-14, AT-15

## Bağlam

- V90 sunucusuz, offline-first, tek kullanıcılı bir uygulamadır; tüm veri cihazdaki şifreli SQLite'tadır (`02-architecture.md §1`). Cloud sync v1'de yoktur (R116.3). Dolayısıyla yedek dosyası, kullanıcının verisini cihaz dışına taşıyabildiği **tek** mekanizmadır.
- Veri iki ayrı depoda yaşar: (1) SQLCipher ile şifreli `v90.sqlite`, (2) app-private dosya sistemi `documentDirectory/photos/` (R116.1). Bu ikisi tek bir DB transaction'ı ile birlikte değiştirilemez; yedekleme ve geri yükleme iki kaynağı birlikte tutarlı tutmak zorundadır.
- DB anahtarı `DbKeyManager` tarafından SecureStore'da `WHEN_UNLOCKED_THIS_DEVICE_ONLY` ile saklanır (02 §12.2, ADR-002). DB dosyasının ham kopyası başka bir cihazda açılamaz; anahtar kaybı veri kaybıdır. Yedek, anahtardan bağımsız olmak zorundadır.
- Şema sürümlenir (§92, ADR-006). Yedek dosyasının `schemaVersion`'ı ile uygulamanın şema sürümü farklı olabilir: eski yedek güncel şemaya yükseltilmeli (R95.8), daha yeni yedek reddedilip açıklanmalıdır.
- En katı kısıt R95.7'dir: import başarısız olursa mevcut veri **silinmez ve kısmen değiştirilmez**. R95.1 ise export'un birkaç tabloyu değil tüm kullanıcı verisini kapsamasını ister.
- `03-data-model.md §0/§4`: `TableRegistry` (tablo adı → Zod satır şeması) hem repository hem backup tarafından kullanılan tek kaynaktır; test `TableRegistry` anahtarlarını `sqlite_master` ile karşılaştırır (`schema_migrations`, `command_log` hariç).
- Progress fotoğrafları MB düzeyindedir; `progress_photos` satırı `file_name`, `bytes`, `sha256` taşır (03 §1.8). Fotoğrafların JSON içine gömülmesi bellek ve doğrulama açısından sorunludur.
- Modül haritasında (02 §3) `core/backup/` altında `BackupExporter`, `BackupImporter`, `BackupArchiver` ve backup migrator'lar tanımlıdır; ZIP kütüphanesi `react-native-zip-archive` (alternatif `fflate`) bir soyutlama arkasındadır (02 §2).

## Karar

### K1. Format: tek ZIP, üç bileşen

Dosya adı `v90-backup-<yyyyMMdd-HHmm>.zip`; içeriği:

```
manifest.json   { formatVersion: 1, schemaVersion: <int>, appVersion, createdAtUtc, timeZone,
                  tables: { <table>: rowCount }, photos: { count, totalBytes },
                  dataSha256, photoShas: { "<file_name>": "<sha256>" } }
data.json       { schemaVersion, tables: { profiles: [...], programs: [...], …, settings: [...] } }
photos/<file_name>      // file_name = progress_photos.file_name (= <photoId>.<ext>)
```

- `formatVersion` ZIP yerleşiminin (manifest alanları, dizin adları) sürümüdür; `schemaVersion` DB şema sürümüdür (`PRAGMA user_version`). İkisi bağımsız sürümlenir; `formatVersion` artırımı ayrı bir ADR gerektirir.
- `data.json.tables` anahtar kümesi **tam olarak** `TableRegistry` anahtarlarıdır (`schema_migrations` ve `command_log` hariç). Eksik veya fazla tablo hem export hem import tarafında hatadır; böylece R95.1 "tüm veri" garantisi bir listeye değil, şemayı tanımlayan tek kaynağa bağlanır.
- Satırlar DB kolon adlarıyla ve DB'deki ham değerlerle yazılır; `*_json` kolonları string olarak kalır (çift kodlama yok, round-trip birebir).
- `dataSha256` `data.json` byte içeriğinin SHA-256'sıdır; `photoShas` her fotoğraf dosyası için ayrı sha taşır. `manifest.json` ZIP'e **en son** yazılır; manifest'i olmayan ZIP yarım export sayılır ve import'ta reddedilir.
- ZIP **şifresizdir**; kullanıcı export öncesi uyarılır ve `BackupArchiver` destekliyorsa opsiyonel parola (ZIP AES) sunulur (02 §12.2). DB anahtarı yedeğe hiçbir biçimde girmez (R93.5, R93.6).
- Tarih alanları (`*_at_utc`, `*_date_key`, `time_zone`, `utc_offset_minutes`) yedekte aynen taşınır; import eden cihazın timezone'una göre **yeniden hesaplanmaz** (R112.2, ADR-007).

### K2. Export (`BackupExporter`)

1. Tek okuma transaction'ı: `BEGIN` → `TableRegistry` sırasıyla tüm tablolar `SELECT *` → `COMMIT`. Tutarlı anlık görüntü alınır. Aktif oturum (`workout_sessions.status = 'active'`) varsa export engellenmez; oturum ve `rest_timers` satırı da yedeğe girer.
2. Her satır export öncesinde `TableRegistry` Zod şemasından geçirilir; şemaya uymayan satır export'u **durdurur** (sessizce atlanan satır = eksik yedek).
3. `data.json` temp dizine yazılır, sha hesaplanır.
4. `progress_photos` satırlarına göre (`pending_delete = 0`) dosyalar `photos/` altına kopyalanır; her dosyanın sha'sı `progress_photos.sha256` ile karşılaştırılır; uyuşmazlık export hatasıdır (bozuk yedek üretilmez).
5. `manifest.json` en son yazılır; paylaşım `expo-sharing` ile yapılır (dosya kullanıcı seçimine kaydedilir).

### K3. Import (`BackupImporter.import(zipUri)`): "doğrula → staging'e kur → değiştir"

Canlı DB'ye ve `photos/` dizinine, tüm doğrulamalar bitip staging tamamen hazır olana kadar **tek byte yazılmaz**. Adımlar 02 §12.3'tekiyle aynı; ADR aşağıdaki ek kararları bağlar:

1. ZIP `documentDirectory/import.tmp/` altına açılır. `manifest.json` Zod ile doğrulanır; bilinmeyen `formatVersion` reddedilir; `dataSha256` doğrulanır.
2. `manifest.schemaVersion > current` → reddet: *"Bu yedek daha yeni bir sürümle alınmış. Uygulamayı güncelleyip tekrar dene."* `< current` → `BACKUP_MIGRATORS[v+1 … current]` zinciri `data.json` üzerinde çalıştırılır (DB migration'larıyla eş sürümlü saf JSON dönüşümleri; ADR-006). `== current` → geçilir.
3. Yükseltilmiş `data.json`, her tablo için `TableRegistry` Zod şemasıyla doğrulanır (R95.6, R119.4). Eksik/bilinmeyen tablo ve `manifest.tables[t].rowCount` uyuşmazlığı hatadır.
4. **Staging DB** `v90.import.sqlite`: `EncryptedSqliteProvider` ile canlı DB'nin anahtarıyla oluşturulur; `MigrationRunner.run()` boş DB'yi en son şemaya getirir (bu çalıştırmada `.bak` alınmaz). Tüm satırlar tek `BEGIN IMMEDIATE … COMMIT` içinde yazılır; transaction başında `PRAGMA defer_foreign_keys = ON` (öz-referanslı FK'lar: `scheduled_workouts.rescheduled_to_id`, `personal_records.superseded_by_id`, `meal_logs.copied_from_id`), `COMMIT` öncesi `PRAGMA foreign_key_check` boş olmalı; `COMMIT` sonrası `PRAGMA integrity_check` = `ok`. Hata → staging dosyası silinir, canlı veri dokunulmamıştır.
5. Fotoğraflar `photos.import/` altına kopyalanır; her dosya `manifest.photoShas` ve `data.json`'daki `progress_photos.sha256` ile doğrulanır. Eksik dosya veya sha uyuşmazlığı → `ImportError` ("yedek bozuk"; eksik dosyalar "Ayrıntılar" altında listelenir). Kısmi import yapılmaz.
6. **Atomik değişim** (sıra önemli, her adım tersine alınabilir):
   - a. Ön koşul: aktif oturum yoksa (varsa: *"Önce devam eden antrenmanı bitir veya iptal et."*); `OrphanSweeper` ve `DayRolloverObserver` duraklatılır.
   - b. Canlı DB: `PRAGMA wal_checkpoint(TRUNCATE)` → `close()`.
   - c. `v90.sqlite → v90.pre-import.sqlite` (varsa `-wal` / `-shm` yan dosyaları birlikte).
   - d. `v90.import.sqlite → v90.sqlite`.
   - e. `photos/ → photos.pre-import/`, `photos.import/ → photos/`.
   - f. DB yeniden açılır; `PRAGMA user_version == current` ve hızlı `integrity_check`; ardından `import.commit.json` işaret dosyası yazılır (içerik: `createdAtUtc`, `schemaVersion`, yedek dosya adı).
   - Herhangi bir adımda hata → **ters sırayla** geri alma (e → d → c), canlı DB tekrar açılır, `ImportError`: *"İçe aktarma başarısız; mevcut verin değişmedi."* (02 §15).
   - Process b–f arasında ölürse: `AppBootstrap`, `v90.pre-import.sqlite` var ve `import.commit.json` yok ise değişimi geri alır (**pre-import her zaman kazanır**). Bu kural rename tabanlı değişimi crash'e karşı da güvenli kılar.
7. Başarıda `v90.pre-import.sqlite` ve `photos.pre-import/` **7 gün** saklanır; Settings'te **"Geri al"** aynı adımların tersidir. 7 gün sonunda veya kullanıcı açıkça vazgeçince silinir.
8. İçe aktarma modu yalnızca **"Değiştir"**; **"Birleştir"** v1'de yoktur ve UI'da gösterilmez.
9. Import sonrası: tüm UI store'ları `hydrate()` ile yeniden dolar (R90.7); `OrphanSweeper` bir kez çalışır; yedekten gelen `rest_timers.notification_id` değerleri geçersiz sayılıp bekleyen bildirimler iptal edilir; `running` durumundaki rest timer süresi UTC'den yeniden hesaplanır (R91.3).

### K4. Sürüm evrimi

- Her `MIGRATIONS[k]` için `BACKUP_MIGRATORS[k]` zorunludur (lint kuralı, 03 §2). Backup migrator'lar saf fonksiyondur ve DB'ye dokunmaz; böylece staging'e yazılan veri her zaman güncel şemadadır ve staging DB'de yalnızca "boş → latest" migration çalışır.
- `MigrationFailedScreen`'deki "Yedeği dışa aktar" (ADR-006) eski şemadaki DB'den export üretir; manifest'e DB'nin gerçek `user_version`'ı yazılır ve satırlar `sqlite_master` listesine göre ham olarak alınır (Zod satır doğrulaması gevşek). Bu yedek, uygulama güncellendikten sonra K3-2 ile normal yoldan yükseltilir.

## Değerlendirilen alternatifler (en az 2; her biri için neden reddedildi)

**A. Şifreli DB dosyasının ham kopyası (`v90.sqlite`) + `photos/` kopyası**
Reddedildi: anahtar cihaza bağlı olduğundan (`THIS_DEVICE_ONLY`) yedek başka cihazda veya sıfırlanmış cihazda açılamaz; bu, "yedek" kavramını anlamsız kılar. Şema yükseltmesi canlı dosya üzerinde DB migration'ı gerektirir, JSON tarafında Zod doğrulaması yapılamaz; bozuk dosya import öncesi ayırt edilemez. Anahtarı yedeğe koymak R93.5'i ihlal eder.

**B. Tek JSON dosyası, fotoğraflar base64 gömülü**
Reddedildi: tüm yedek tek `JSON.parse` ile belleğe alınır (fotoğraflarla onlarca MB → düşük RAM'li cihazlarda çökme, R117.1 riski); base64 boyutu ~%33 artırır; dosya başına sha doğrulaması ve kısmi bozulma tespiti yapılamaz; R95.3 fotoğraflar için **ayrı** medya stratejisi ister.

**C. Canlı DB üzerinde in-place import (tek transaction'da `DELETE` + `INSERT`)**
Reddedildi: `photos/` dizini transaction dışındadır; DB rollback olsa bile dosya değişiklikleri yarım kalabilir → R95.7 ihlali. Yedek daha eski şemadaysa canlı DB'de karma bir "JSON + DB" migration yolu gerekir. Import süresince uygulama canlı DB'yi kilitler; hata anında "hiçbir şey değişmedi" garantisi, dosya değişimindeki kadar basit ve doğrulanabilir değildir (staging'de `integrity_check` + `foreign_key_check` **değişimden önce** çalışır).

**D. Tablo başına CSV/NDJSON dosyaları**
Reddedildi: CSV `NULL` ile boş string'i ve iç içe JSON kolonlarını (`*_json`) güvenilir ayırt edemez; Zod satır şemaları JSON nesnesi bekler; çok dosyalı yerleşim manifest karmaşıklığını artırır. NDJSON'un streaming avantajı, ileride `formatVersion: 2` için (çok büyük `set_logs` tabloları) yeniden değerlendirilebilir; v1 hacmi için gerekli değildir.

**E. iCloud / Google cihaz yedeğine güvenmek**
Reddedildi: R116.3 cloud sync'i v1'de kapatır; cihaz yedeği DB dosyasını taşısa da anahtar `THIS_DEVICE_ONLY` politikasıyla yeni cihaza gelmez (ADR-002) → geri yüklenemez. Kullanıcının kontrolünde, anahtardan bağımsız bir yedek şarttır.

**F. "Birleştir" (merge) modlu import**
Reddedildi (v1 kapsamı dışı): kimlik çakışmaları, `UNIQUE` kısıtlar (`ux_sessions_single_active`, `ux_sched_one_open`, `check_ins.local_date_key`) ve program state'inin (`training_sequence_index`) birleştirilmesi için çatışma çözüm kuralları gerekir; bunların hatalı olması sessiz veri bozulmasına yol açar. "Değiştir" modu + pre-import "Geri al" daha güvenlidir.

## Sonuçlar (olumlu / olumsuz / riskler ve azaltımlar)

**Olumlu**
- R95.1 garantisi bir listeye değil `TableRegistry`'ye bağlıdır; yeni tablo eklenip registry'ye girmezse test kırılır, yedek eksik kalamaz.
- Canlı veri, tüm doğrulamalar (manifest, sha, Zod, migration, `integrity_check`, `foreign_key_check`, fotoğraf sha) bittikten sonra ve yalnızca rename işlemleriyle değişir; geri alma ve "Geri al" aynı basit mekanizmadır (R95.7, AT-15).
- Yedek anahtardan bağımsızdır; cihaz değişimi ve sıfırlama senaryolarında çalışır (AT-14).
- Eski yedekler `BACKUP_MIGRATORS` ile yükselir; yeni yedekler açıklamayla reddedilir (R95.8).
- `ImportError`, `MigrationFailedError` gibi hata sınıfları ve Türkçe mesajları 02 §15 taksonomisine oturur (R117.3, R117.5).

**Olumsuz**
- Import sırasında geçici olarak ~2× DB + ~2× fotoğraf disk alanı gerekir; 7 gün boyunca `pre-import` kopyaları yer kaplar.
- Export ZIP şifresizdir; hassas sağlık verisi (R93.1) kullanıcının seçtiği yere açık biçimde çıkar. Uyarı ve opsiyonel parola sunulur, ancak sorumluluk kullanıcıdadır.
- Her DB migration'ı bir backup migrator gerektirir (bakım maliyeti; lint ile zorlanır).
- Aktif antrenman varken import yapılamaz (bilinçli kısıt; R90 garantileriyle çelişmemek için).

**Riskler ve azaltımlar**

| Risk | Azaltım |
|------|---------|
| Değişim adımları (c–e) arasında process ölür | `import.commit.json` işaret dosyası; işaret yoksa `AppBootstrap` pre-import'u geri getirir (pre-import her zaman kazanır). |
| Disk alanı yetersiz | Import başında gereken alan (ZIP açılmış boyut + DB + fotoğraf) hesaplanır; yetersizse hiçbir adım başlamaz, Türkçe açıklama gösterilir. |
| ZIP kütüphanesi native modül sorunları / büyük dosya | `BackupArchiver` soyutlaması; `fflate` yedek uygulama; büyük fotoğraf setlerinde streaming kopyalama. |
| `OrphanSweeper` değişim sırasında çalışıp dosya siler | Import süresince sweeper duraklatılır; değişim bittikten sonra tek sefer çalıştırılır. |
| Backup migrator ile DB migration'ı sürüklenir (aynı sürüm, farklı dönüşüm) | Lint (her `MIGRATIONS[k]` için `BACKUP_MIGRATORS[k]`) + parite testi: `v(k)` fixture DB'sinden export → `BACKUP_MIGRATORS` ile yükselt ↔ aynı fixture'ı `MigrationRunner` ile yükseltip export et; iki `data.json` eşit olmalı. |
| Yedekten gelen `notification_id` yeni cihazda yabancı bildirimi işaret eder | Import sonrası tüm bekleyen yerel bildirimler iptal edilir; `running` timer UTC'den yeniden hesaplanır. |
| Kullanıcı yanlış yedeği içe aktarır | 7 günlük "Geri al"; import öncesi özet ekranı (yedek tarihi, `appVersion`, tablo satır sayıları, fotoğraf sayısı). |

## Doğrulama (hangi test/kabul senaryosu bu kararı doğrular)

- **AT-14** (E2E, Maestro): veri oluştur → export → uygulama sıfırla → import → tüm ekranlarda veri geri geldi; fotoğraflar açılıyor.
- **AT-15** (integration + E2E): bozuk ZIP, eksik manifest, yanlış `dataSha256`, Zod hatası, eksik fotoğraf, staging `integrity_check` hatası, değişim adımı c/d/e'de enjekte edilen hata → canlı `v90.sqlite` byte-hash'i ve `photos/` listesi import öncesiyle **aynı**; `ImportError` mesajı gösterildi.
- **Integration – round-trip:** fixture DB → `BackupExporter` → `BackupImporter` (staging) → tüm tabloların satır sayıları ve `SELECT *` içeriği birebir eşit (R95.1); `TableRegistry` anahtarları == `sqlite_master` (03 §4 testi).
- **Integration – sürüm kontrolü:** `schemaVersion = current + 1` → reddedildi, mesaj doğru; `schemaVersion = k < current` fixture yedeği → `BACKUP_MIGRATORS` zinciriyle yükseltildi ve import başarılı (R95.8).
- **Integration – crash kurtarma:** değişim adımı d'den sonra process öldürülür (test harness'ta) → yeniden açılışta `import.commit.json` yok → pre-import geri getirildi, veri değişmedi.
- **Unit:** manifest Zod şeması; `photoShas` doğrulama; `defer_foreign_keys` ile öz-referanslı FK satırlarının yazılabildiği.
- **Lint/test:** her `MIGRATIONS[k]` için `BACKUP_MIGRATORS[k]` mevcut; backup migrator ↔ DB migration parite testi.
- **Manuel (05-acceptance-tests.md):** gerçek cihazda düşük disk alanıyla import; "Geri al" akışı; parola korumalı ZIP (destekleniyorsa).
